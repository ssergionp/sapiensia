# Backup noturno no R2 e restauração testada (#40) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Status:** APROVADO pelo Sérgio em 16/11/2026, com dois ajustes: **D2 = 30 diários + 3 mensais** (o inventário de dados pessoais registra esse prazo) e **D5 = (b), duas execuções por dia** (o ADR-0002 passa a dizer "duas vezes por dia" no lugar de "toda noite"). D1, D3, D4 e D6 a D12 aceitas como recomendado. Execução por subagent-driven-development. A implementação **não começou**: o Sérgio vai reiniciar o computador (WSL/Docker) antes.

**Goal:** Duas vezes por dia o banco é copiado, já criptografado, para um bucket privado do Cloudflare R2; uma falha avisa o Sérgio; e a restauração é provada no CI (ida e volta) e de verdade na homologação, com o tempo medido.

**Architecture:** Um workflow agendado do GitHub Actions (`backup.yml`) roda `scripts/backup/backup.sh`: `pg_dump` (formato custom, só o schema `public`) sai por um pipe direto para o `age`, que criptografa com a chave pública guardada no repositório; só o arquivo `.age` toca o disco do runner e sobe ao R2 pela AWS CLI. A chave privada fica só com o Sérgio, fora do GitHub. A restauração é o `scripts/backup/restore.sh`, o mesmo script no CI e no runbook. **Nenhuma linha de Java, nenhuma rota, nenhuma tela, nenhuma dependência nova no backend nem no frontend.**

**Tech Stack:** GitHub Actions (`schedule` + `workflow_dispatch`), bash, `pg_dump`/`pg_restore` pela imagem Docker `postgres:<major>`, age v1.3.2, AWS CLI (já vem no runner), Cloudflare R2 (API S3), Node `--test` para o teste estático do workflow.

**Spec:** issue #40 (pai #5); `docs/adr/0002-banco-e-arquivos-no-supabase-com-backup-no-r2.md`; `docs/spec/sapiensia-spec.md` linhas 572 (NFR-007) e 573 (NFR-008); `docs/runbooks/homologacao-fly.md` (seção "Banco"). Documentação oficial consultada em 16/11/2026: R2 [tokens](https://developers.cloudflare.com/r2/api/tokens/), [bucket locks](https://developers.cloudflare.com/r2/buckets/bucket-locks/), [lifecycle](https://developers.cloudflare.com/r2/buckets/object-lifecycles/), [preços](https://developers.cloudflare.com/r2/pricing/), [AWS CLI](https://developers.cloudflare.com/r2/examples/aws/aws-cli/); GitHub [evento schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows); Supabase [backup e restauração](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore); [age v1.3.2](https://github.com/FiloSottile/age/releases/latest).

## Global Constraints

- O dump em texto aberto **nunca** vai para: disco do runner, log, artefato do Actions, cache ou R2. Ele só existe dentro do pipe `pg_dump | age`. O workflow de backup não usa `upload-artifact` nem `cache`.
- A chave privada do age nunca entra no GitHub, no Fly nem no repositório. No CI, o teste de ida e volta gera um par descartável na hora.
- Nenhum segredo na linha de comando: senha do banco por `PGPASSWORD`, chaves do R2 por `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`, sempre vindos de `secrets.*`. `pg_dump` sem `--verbose`.
- Actions fixadas por SHA (como no `ci.yml`); o workflow de backup só usa `actions/checkout`. `permissions:` mínimas (`contents: read`, `issues: write`).
- O backup lê o banco com um papel só de leitura (`backup_reader`), nunca com o usuário da aplicação (ressalva na D6).
- Scripts em bash com `set -euo pipefail`, LF. Saída dos scripts em inglês; runbook e textos da seção 6 em pt-BR, exatamente como escritos lá.
- Testes locais: só lint e testes focados, um comando pesado por vez. O check que vale é o do CI.
- Cada verificação que prova requisito leva o ID no título (nome do passo do CI, linha `PASS`/`FAIL` do script, nome do teste Node).

## Review Focus

1. **Papel de backup sem permissão numa tabela criada depois** (migration nova): o `pg_dump` falha com erro e o alerta dispara; nunca um backup "verde" sem a tabela. Teste na Task 1 (tabela criada depois do `grant`).
2. **Tabela com RLS ligado** (o Supabase deixa a função `rls_auto_enable` no `public`): o dump sai completo ou falha alto; nunca um dump com zero linhas. Teste na Task 1.
3. **Dump truncado** (conexão cai no meio): `pipefail` derruba o script e nada sobe ao R2. Teste na Task 1 (`pg_dump` apontado para porta fechada: sem arquivo, saída diferente de zero).
4. **Chave errada ou arquivo corrompido na restauração:** `restore.sh` para antes de tocar o banco de destino. Teste na Task 1.
5. **Segunda execução no mesmo dia** (reexecução manual): a chave do objeto leva a hora, então não tenta sobrescrever um objeto travado. Teste na Task 1 (nome do objeto).

**Recomendação: GitHub Actions.** Não depende do Fly acordado nem da aplicação saudável, não mexe na imagem e é a opção com menos código.

Detalhes fixados:
- **Horário (D5):** `cron: '17 7,19 * * *'` (UTC) = 04:17 e 16:17 de São Paulo. Duas execuções por dia: se o GitHub descartar uma, o intervalo sem backup fica em 24 h, ainda dentro do RPO; em dia normal é de 12 h. A da madrugada roda depois da conciliação das 03:30; ambas fora da hora cheia (a documentação avisa que a hora cheia é o pico de atrasos).
- **Ambientes:** hoje só existe a homologação; a produção entra no #43 repetindo os passos da seção 7 com segredos próprios. O workflow recebe o ambiente (`homolog`; `prod` depois) e lê os segredos daquele ambiente.
- **Conexão:** pooler do Supabase em modo sessão (o mesmo host do `DB_URL`), porque o runner do GitHub não tem IPv6 e a conexão direta do Supabase é só IPv6.
- **Versão do cliente:** `pg_dump` da imagem `postgres:<major>` igual à do servidor (`PG_MAJOR` como variável do ambiente; o Sérgio confere com `show server_version;`). O script compara e para se forem diferentes. O runner traz o cliente 16, mais velho que o Supabase atual.
- **O que entra no dump:** `--format=custom --schema=public --no-owner --no-privileges`. Tudo que o Flyway criou está no `public` (inclusive `flyway_schema_history` e `scheduled_tasks`). Os schemas do próprio Supabase (`auth`, `storage`...) ficam de fora: a aplicação não os usa e eles não restauram limpo em outro projeto.
- **Efeito colateral bom:** o Supabase Free pausa projeto sem atividade por 7 dias; a conexão de cada backup conta como atividade. Se pausar mesmo assim, o backup falha e avisa.

## 2. Criptografia (item b)

- **age v1.3.2**, modo destinatário: a chave pública (`age1...`) fica em `scripts/backup/age-recipients.txt`, no repositório; quem tem só ela consegue criptografar e não consegue ler. Chave pública não é segredo.
- A chave privada (`AGE-SECRET-KEY-...`) é gerada pelo Sérgio no computador dele (`age-keygen`) e guardada no Bitwarden **e** numa segunda cópia fora do computador (D3). **Perder a chave privada inutiliza todos os backups**; não existe recuperação.
- No runner o age é baixado da release fixada (v1.3.2) e conferido por SHA-256 escrito no script; sem `apt` (os espelhos já ficaram fora do ar no CI). O hash é obtido na Task 1 a partir da release oficial.
- Fluxo: `pg_dump ... | age -R age-recipients.txt -o "$RUNNER_TEMP/<nome>.dump.age"`. Conferências antes de subir: `pipefail`, arquivo começa com `age-encryption.org/v1`, não contém a marca `PGDMP`, tamanho acima de um mínimo.
- Arquivo de destinatários vazio ou inválido: o script para com erro (nunca sobe em texto aberto como alternativa).

## 3. R2: bucket, credencial e retenção (item c)

- **Um bucket privado por ambiente:** `sapiensia-backup-homolog` (e `sapiensia-backup-prod` no #43), sem domínio público e sem `r2.dev`. Segredos separados por ambiente (SEC-071).
- **Credencial:** o R2 **não tem permissão só de escrita**. Os níveis são Admin Read & Write, Admin Read only, Object Read & Write e Object Read only. O menor que grava é **Object Read & Write restrito àquele bucket**: não cria, não apaga nem configura bucket, mas lê, lista e grava objetos.
- **O que compensa a falta do "só escrita":**
  - quem roubar a credencial lê apenas arquivos criptografados (inúteis sem a chave privada);
  - **bucket lock** (trava do R2): impede apagar **e sobrescrever** cada objeto durante o prazo, mesmo com a credencial. Regras por prefixo.
- **Retenção (D2: 30 dias de backups diários + 3 mensais), tudo por regra do R2, nada por código:**

| Prefixo | Quando grava | Bucket lock | Lifecycle (apaga) |
|---|---|---|---|
| `daily/` | toda execução (duas por dia: ~60 objetos em 30 dias) | 30 dias | 30 dias |
| `monthly/` | na execução da madrugada do dia 1 de cada mês (segundo envio do mesmo arquivo) | 93 dias | 93 dias |

  Noventa e três dias guardam sempre os 3 últimos mensais (três meses seguidos somam no máximo 92 dias). A trava vence antes de a regra de ciclo de vida apagar (a documentação diz que a trava tem precedência e que a remoção acontece em até ~24 h depois do prazo).
- **Nome do objeto:** `daily/<AAAA-MM-DD>T<HHMM>Z.dump.age`. A hora no nome evita sobrescrever um objeto travado numa reexecução.
- **Conferência do envio:** `head-object` depois do upload, comparando o tamanho com o do arquivo local.
- **AWS CLI:** endpoint `https://<ACCOUNT_ID>.r2.cloudflarestorage.com`, região `auto`, com `AWS_REQUEST_CHECKSUM_CALCULATION=when_required` e `AWS_RESPONSE_CHECKSUM_VALIDATION=when_required`. A página do R2 para a AWS CLI não fala dos checksums novos da CLI; a tabela de compatibilidade do R2 mostra suporte parcial a CRC32. **Isso só fica provado na primeira execução real** (Task 4); se falhar, o plano B é `curl --aws-sigv4` com um único PUT.
- **Consequência de privacidade:** um Cliente anonimizado (#41) continua existindo nos backups por até 93 dias (cerca de 3 meses), e a trava impede apagar antes. Entra no inventário de dados pessoais e no runbook ("depois de restaurar, refazer as anonimizações pedidas depois da data do backup"). Ver D2.

## 4. Restauração (item e)

**4.1 Runbook** `docs/runbooks/backup-e-restauracao.md` (comandos em PowerShell, um por linha, com uma frase explicando cada um):
1. Do que você precisa além do dump: chave privada do age e os segredos do Fly que estão no Bitwarden (sem a `APP_MFA_ENCRYPTION_KEY` original o MFA gravado não funciona, ADR-0004).
2. Baixar o arquivo do R2 (pelo painel da Cloudflare; a credencial do backup não fica no computador).
3. Criar o banco novo (projeto novo no Supabase, mesma versão do PostgreSQL).
4. `just backup-restaurar <arquivo.age> <chave.txt>`: descriptografa numa pasta temporária, roda `pg_restore` pela imagem `postgres:<major>`, apaga o texto aberto no fim (inclusive se der erro).
5. Conferir: lista de tabelas e contagens (o script imprime), `flyway_schema_history` na última versão.
6. Apontar a aplicação para o banco novo (`fly secrets set DB_URL/DB_USER/DB_PASSWORD`), conferir o health check e um login.
7. Depois: refazer anonimizações pendentes, rodar a conciliação (`docs/runbooks/conciliacao-asaas.md`) para os Pedidos perdidos no intervalo, recriar o papel `backup_reader` no banco novo e atualizar os segredos do backup.
8. Tabela "Exercícios de restauração" (data, ambiente, backup usado, tempo de cada etapa, resultado).
9. O que este backup **não** cobre: os PDFs e as capas no Supabase Storage (seção 8).

**4.2 Teste automatizado de ida e volta no CI** (`scripts/backup/roundtrip-test.sh`, no fim do job `e2e`, que já tem a aplicação real, o Flyway aplicado e dados criados pelos testes de ponta a ponta):
1. para o contêiner da aplicação (as contagens não podem mudar no meio);
2. cria o papel com `scripts/backup/create-backup-role.sql`, depois cria uma tabela nova e liga RLS numa tabela (Review Focus 1 e 2), e uma função `rls_auto_enable` no `public` como a do Supabase;
3. gera um par de chaves age descartável;
4. roda **o mesmo** `backup.sh` da noite, sem o envio (`BACKUP_SKIP_UPLOAD=1`);
5. confere que o arquivo é age e não tem `PGDMP`;
6. tenta restaurar com outra chave: tem de falhar sem tocar o destino;
7. roda **o mesmo** `restore.sh` do runbook num banco novo (`restore_check`) que já tem a função `rls_auto_enable`, como um projeto novo do Supabase;
8. compara origem e destino: mesma lista de tabelas do `public`, mesma contagem exata em cada tabela, mesmo valor das sequências, mesma última versão no `flyway_schema_history`;
9. confere que não sobrou arquivo em texto aberto.

## 5. Alerta de falha (item d)

Rodando no Actions, o `AdminAlerts` não participa. Três camadas:
1. **Issue no repositório:** passo `if: failure()` roda `gh issue create` (ou comenta na issue aberta com o rótulo `backup-failure`, para não abrir uma por execução). O GitHub manda e-mail ao Sérgio por ser dono do repositório. O texto só leva data, ambiente e o link da execução; nunca saída do `pg_dump`.
2. **E-mail de falha do Actions:** a documentação diz que as notificações de workflow agendado vão para quem alterou o `cron` por último. Por isso o commit que cria o `cron` precisa ser de autoria do Sérgio (já é o autor git configurado) e a notificação de Actions precisa estar ligada na conta (seção 7).
3. **O que nenhuma das duas pega:** execução que o GitHub descartou ou workflow desligado. Não há falha, logo não há alerta. Ver D5.

Fechar a issue é manual, depois de uma execução verde (o runbook explica).
