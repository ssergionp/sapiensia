# #132 Demonstração e teste de ponta a ponta do estorno — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

Plano do modo noturno: as decisões marcadas **DECIDIDO NO MODO NOTURNO — conferir** não tiveram o OK do Sérgio antes da execução.

**Goal:** Dar à demonstração local um jeito de "estornar" um Pedido pago (`just demo-estornar <id do Pedido>`) e provar o fluxo de estorno num teste de ponta a ponta: compra, pagamento, estorno, o Produto some da Biblioteca e o Pedido aparece como "Reembolsado" (FR-020, FR-023, FR-025).

**Architecture:** O estorno de verdade acontece no Asaas; o sistema só observa: recebe `PAYMENT_REFUNDED` no webhook e o `RefundConfirmation` confirma lendo a cobrança (`GET`), que precisa voltar `REFUNDED`. Hoje o `FakePixGateway` (perfil local) e o stub do Asaas do CI (`.github/asaas-stub.mjs`, contra o qual o e2e do CI roda no perfil `prod`) respondem sempre `RECEIVED`. Os dois ganham um estado "estornado", cada um com um gatilho próprio, e o resto do caminho (webhook → `RefundConfirmation` → telas) é o código de produção, sem atalho.

**Tech Stack:** Java 25 / Spring Boot 4.1 / Spring Security; Node (scripts `.mjs` com `node:test`); Playwright.

**Spec:** issue #132 (Refs #36, decisão D5 de `docs/superpowers/plans/2026-11-15-36-reembolso.md`).

## Decisões

- **P1 — DECIDIDO NO MODO NOTURNO — conferir:** rota só da demonstração `POST /api/local-demo/charges/{chargeId}/refund` → 204 (404 se a cobrança não existe no Fake). O controller só existe com `app.pix.provider=fake` (`@ConditionalOnProperty`, igual ao `FakePixGateway`, que já recusa subir com o perfil `prod`). **Não é `permitAll`:** usa a mesma credencial do webhook (`.access(asaasWebhookAccess)`: token `asaas-access-token` + IP da lista), e fica fora do CSRF como o webhook (quem chama é um script, sem sessão). Sem a rota, o script não teria como mudar o estado em memória do Fake, que vive no processo da API.
- **P2 — DECIDIDO NO MODO NOTURNO — conferir:** o stub do CI ganha `POST /v3/__e2e/payments/<id>/refund` (mesma checagem do `access_token` do stub), que passa a cobrança para `REFUNDED`; o `GET /v3/payments/<id>` devolve o estado guardado (`RECEIVED` por padrão, como hoje).
- **P3:** um único teste e2e; o gatilho do estorno escolhe pelo ambiente: com `E2E_ASAAS_STUB_URL` (definida no job e2e do `ci.yml`) chama o stub; sem ela (local, perfil `local` com o Fake) chama a rota de P1. Depois do gatilho, o teste manda `PAYMENT_REFUNDED` ao webhook real, como o teste de pagamento já faz com `PAYMENT_RECEIVED`.
- **P4:** `scripts/demo-estornar.mjs` reaproveita `parseOrderId`, `apiBaseUrl`, `findChargeId` e `LOCAL_WEBHOOK_TOKEN` exportados do `scripts/demo-pagar.mjs` (sem copiar). Primeiro a rota de P1, depois o webhook `PAYMENT_REFUNDED`.
- **P5:** sem migration (V28/V29 não usadas), sem dependência nova.
- **P6 (do /code-review) — DECIDIDO NO MODO NOTURNO — conferir:** (a) a regra da rota de P1 e a exceção de CSRF só entram na `SecurityConfig` quando `app.pix.provider=fake`; com o Asaas de verdade a rota cai no `denyAll` de `/api/**`, e o e2e do CI (perfil prod) confere 403 com o token válido. (b) O script só estorna Pedido `PAID`: lê o estado no banco local (como já lê a cobrança) e, se não for pago, para com uma mensagem, sem chamar a API (um estorno antes do pagamento deixaria a cobrança fictícia estornada para sempre e o Pedido travado). (c) No CI, `E2E_ASAAS_STUB_URL=http://127.0.0.1:54322`. (d) O helper de webhook do e2e vira um só (evento e estado como parâmetros). Fora: extrair a publicação de Produto do e2e (já repetida nos testes antigos); o teste do script que confere a importação por texto.

- Outro status: `A API respondeu <status>.`
- Sucesso: `Estorno enviado. Em alguns segundos o Pedido aparece como Reembolsado e o Produto sai da Biblioteca.`

## Global Constraints

- Rota nova em /api começa negada; libere com a credencial do webhook, nunca `permitAll` (P1).
- Fluxo crítico (estorno) ganha teste em `frontend/e2e/` contra API e banco de verdade, sem `page.route` nem mocks.
- Valor que imita segredo montado em tempo de execução (gitleaks), como o `LOCAL_WEBHOOK_TOKEN` do e2e.
- Log sem token nem dado pessoal.
- Testes: só focados, um pesado por vez; cada teste novo falha por asserção antes do código.

## Review Focus

1. A rota de P1 chamada sem token ou com token errado → recusada, como o webhook (teste).
2. Rota de P1 com o provedor de verdade → não existe (teste de contexto com `app.pix.provider` diferente seria um contexto novo: em vez disso, o teste confere a anotação `@ConditionalOnProperty` no controller).
3. Estorno de cobrança que não existe → 404, sem mudar nada (teste).
4. Estorno antes do pagamento (cobrança `PENDING`) → o Fake marca `REFUNDED`; o `RefundConfirmation` decide como decide em produção (não é caso da demonstração; só registrado).
5. O e2e no CI (perfil prod + stub) e local (Fake) pelo mesmo teste → P3.
