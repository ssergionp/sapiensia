# Demo: arquivos que sobrevivem à remoção de uma worktree (#147) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task.

**Status:** plano curto auto-aprovado (pedido do Sérgio em 16/11/2026). Decisões conservadoras marcadas **conferir**.

**Goal:** Na demonstração, Download e capas continuam funcionando depois que uma worktree que rodou `just demo` é removida.

**Causa (da issue):** o banco `app_demo` é um só para todas as pastas, mas `scripts/demo.ps1` grava os arquivos em `../.tmp/demo/storage` relativo à pasta que rodou a demo. O `just limpar-ticket` apaga a worktree com os arquivos, e o `DemoProductSeeder` pula o Produto porque o banco diz que ele já tem arquivo.

**Architecture:** duas mudanças pequenas, as duas sugeridas na issue:
1. `scripts/demo.ps1` aponta `APP_STORAGE_FILE_DIR` para `<pasta principal>/.tmp/demo/storage` (caminho absoluto), achando a pasta principal com `git rev-parse --git-common-dir`. Assim a pasta principal e todas as worktrees usam os mesmos arquivos, como já usam o mesmo banco.
2. `DemoProductSeeder` também confere os Produtos de demonstração **já publicados**: se o objeto do PDF ou da capa atual não existe na storage, envia um novo pelos serviços de sempre (`ProductFileService.upload` com `reauthenticated = true`, `ProductCoverService.upload`), que trocam a chave na linha. Isso conserta bancos `app_demo` já quebrados sem apagar nada.

**Tech Stack:** PowerShell 5.1, Java 25 / Spring Boot, JUnit 5 + Testcontainers.
