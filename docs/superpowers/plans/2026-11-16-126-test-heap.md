# Limitar o heap da JVM de teste e medir o check (#126) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task.

**Status:** plano curto auto-aprovado (pedido do Sérgio em 16/11/2026). Decisões conservadoras marcadas **conferir**.

**Goal:** A JVM dos testes do backend passa a ter um teto de heap (local e no CI), com o menor valor que deixa a suíte inteira verde, e o `just check-rapido` com todos os testes do backend é medido (memória livre mínima, contêineres simultâneos, tempo) e comparado com o CI.

**Situação (da issue, origem #122):** o surefire não define heap; a JVM de teste usa o padrão (1/4 da RAM, ~4 GB de máximo) e o heap cresce sem limite prático. Com o IntelliJ aberto (16 GB), a memória livre caiu a 2,90 GB aos 81 s.

**Architecture:** uma propriedade no `backend/pom.xml` (`<argLine>` do surefire, via a propriedade `argLine`), sem plugin novo nem dependência nova. Um teste pequeno prova que o teto está ativo na JVM de teste. A medição é feita uma vez, fora do código, e o resultado vai para este plano e para a PR.

**Tech Stack:** Maven Surefire (herdado do `spring-boot-starter-parent` 4.1.2), JUnit 5, PowerShell para a amostragem.

## Global Constraints
- Nada de código de produção muda. Nenhuma dependência nova.
- O teto vale para o CI também (o `pom.xml` é o mesmo); o CI tem de continuar verde.
- Valor: o **menor** entre 512m, 768m e 1g (nessa ordem) que deixa a suíte inteira do backend verde localmente; **conferir**: se 512m passar raspando (OutOfMemoryError intermitente ou GC excessivo, tempo > 20% maior que com 1g), usar o próximo degrau.
- `MAVEN_OPTS` / heap do processo do Maven: **fora** (opcional na issue; conservador não mexer), só medido.
- Um comando pesado por vez. A suíte inteira roda localmente só nesta medição (é o pedido da issue).
- **Conferir:** o IntelliJ não está aberto nesta máquina agora (nenhum `idea64`); a medição registra isso e a memória livre no início, e fica a recomendação de o Sérgio repetir com o IntelliJ aberto.

## Tasks

### Task 1: teto de heap na JVM de teste
**Files:** Modify `backend/pom.xml` (`<properties>`: `<argLine>-Xmx<valor></argLine>`); Create `backend/src/test/java/br/com/sergio/sapiensia/TestJvmHeapTest.java`.
- [ ] Teste (vermelho por asserção): `Runtime.getRuntime().maxMemory()` da JVM de teste é no máximo 1 GiB. Título: `shouldRunTheTestsWithABoundedHeap`. Hoje falha (~4 GB).
- [ ] Rodar só ele: `cd backend; .\mvnw.cmd test -Dtest=TestJvmHeapTest`.
- [ ] Adicionar `argLine` com 512m; rodar só o teste (verde).
- [ ] Achar o valor: rodar a suíte inteira do backend (`.\mvnw.cmd test`) com 512m; se falhar por memória, 768m; depois 1g. Registrar para cada tentativa: resultado, tempo, erros de memória.
- [ ] `just lint`; commit `chore: bound the heap of the test JVM (#126)`.

### Task 2: medir o `just check-rapido` completo
- [ ] Com o valor escolhido, rodar `just check-rapido` (a mudança no `pom.xml` faz ele rodar todos os testes do backend) com uma amostragem a cada 5 s em segundo plano (script no scratchpad, não versionado): memória livre (`Win32_OperatingSystem.FreePhysicalMemory`), soma do working set dos processos `java`, `vmmemWSL`, número de contêineres (`docker ps -q`).
- [ ] Comparar o tempo dos testes do backend com o do CI (último run verde da `main`, job `check`).
- [ ] Gravar a tabela de resultados na seção "Resultados" deste plano; commit `docs: test heap measurement for the full quick check (#126)`.

### Fim
`just check-rapido` (já rodado na Task 2); skill `verificar-entrega`; push `chore/126-test-heap`; PR `Closes #126`; CI verde.

## Riscos

- Um `argLine` futuro (ex.: JaCoCo) sobrescreveria este: o teste da Task 1 acusa.
